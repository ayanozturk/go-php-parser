# Mago 1.47.4 same-machine rebaseline, 2026-08-25

## Outcome

This rebaseline is **rejected for milestone comparison**. It does not support setting delivery dates or claiming that go-php-parser is faster than Mago.

The current Mago release was verified as 1.47.4 from GitHub's live release metadata. Its Apple ARM64 archive matched the published SHA-256 before extraction. The run used the three pinned repository revisions already declared in `test_projects/manifest.json`, populated Composer dependencies, and selected the same source/include boundaries for both tools.

Two workloads failed validation before measurement:

| Workload | Selected PHP files | Parsed | Failed | Decision |
| --- | ---: | ---: | ---: | --- |
| PSL | 3,361 | 3,296 | 65 | Reject; do not time a parser-skipping run. |
| Magento | 41,848 | 41,833 | 15 | Reject; do not time a parser-skipping run. |

WordPress parsed all 5,357 selected PHP files and proceeded to ten interleaved process-cold runs. Both tools missed the variance gate, and Mago's count formatter did not expose analysed-file accounting. More importantly, Mago emitted 218,741 findings under its strict configuration while go-php-parser emitted 29,000 under all currently registered rules. The outputs are not semantically comparable.

## WordPress measurements

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| go-php-parser | 1.048s | 1.015s | 1.00s | 1.21s | 0.072s | 6.90% | 1,083,883,520 bytes |
| Mago 1.47.4 | 3.086s | 3.05s | 2.83s | 3.33s | 0.158s | 5.11% | 1,225,932,800 bytes |

The raw ratio is 0.340x for elapsed time and 0.884x for peak RSS. These are contextual observations only. They fail the contract because variance exceeds 5%, Mago file accounting is unknown, and semantic coverage differs materially.

Go accounting was stable in every measured run: 5,357 discovered, 5,357 parsed, zero failed, 1,451,208 LOC, 47,344,277 bytes, and 29,000 diagnostics. Mago's diagnostic counts were also stable: 143,188 errors, 72,386 warnings, 3,129 help findings, and 38 notes.

## Benchmark correction

The rebaseline found that `cmd/benchmark` previously started its cold timer only after discovery, reads, and parsing. That violated the comparable-performance contract. Cold/index subprocess timings now come from the parent process boundary and therefore include binary startup, discovery, reads, parsing, indexing, analysis, reduction, and worker-result serialization. Previously published cold numbers from this harness must not be treated as full-analysis timings.

The harness also now accepts `--paths` and `--excludes`, records both in JSON, rejects root escapes and missing configured paths, and deduplicates overlapping scan roots. Checked-in Mago configurations under `benchmark-configs/mago` define the reference path and rule boundaries used here.
